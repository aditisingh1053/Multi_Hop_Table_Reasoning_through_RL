## Q1. HybridQA: data format, how to get it, gold evidence annotations, statistics, evaluation, Hugging Face copy

### Takeaway
HybridQA is the right primary benchmark. It has 62,682 / 3,466 / 3,463 questions, each grounded in one Wikipedia table (about 15.7 rows x 4.4 columns, about 44 linked passages). Answer-node locations (`[cell_text, [row, col], link, "table"|"passage"]`) appear only in the auto-generated `train.traced.json` and `dev.traced.json`, not in the human-annotated `train/dev.json`. They come from approximate string-matching: the dataset's lead author's follow-up paper (OTT-QA) estimates about 15% error, and 46% of dev questions have more than one candidate node. Test answers are hidden and scored through CodaLab. The Hugging Face copy is a loading script that cannot run on `datasets` >= 4.0 and does not include answer nodes.

**Gold evidence: `answer-node` format** (verified by parsing the traced files)
- Example from `dev.traced.json`: `"answer-node": [["Emmitt Smith", [0, 1], "/wiki/Emmitt_Smith", "passage"], ["Walter Payton", [1, 1], "/wiki/Walter_Payton", "passage"], ...]` for the question "What is the middle name of the player with the second most NFL career rushing yards?" (answer "Jerry"). — [dev.traced.json](https://raw.githubusercontent.com/wenhuchen/HybridQA/master/released_data/dev.traced.json)
- Each node is `[cell_text, [row_index, col_index], link_or_null, source]`. `row_index` indexes the table's `data` array with the header excluded: `[0,1]` = data row 0, column "Player" = "Emmitt Smith" in [tables_tok/List_of_National_Football_League_rushing_yards_leaders_0.json](https://raw.githubusercontent.com/wenhuchen/WikiTables-WithLinks/master/tables_tok/List_of_National_Football_League_rushing_yards_leaders_0.json).
  - A `"passage"` node gives the hyperlink of the passage that contains the answer, reached through that cell.
  - A `"table"` node has link `null`; the answer is the cell text itself, e.g. `['524 km', [6, 1], None, 'table']`.
  - In dev, all 7,207 passage nodes have a link and all 2,838 table nodes have `null` (my parse of [dev.traced.json](https://raw.githubusercontent.com/wenhuchen/HybridQA/master/released_data/dev.traced.json)).
- Node counts (my parse): train has 135,813 passage nodes and 54,171 table nodes (3.03 nodes per question); dev has 7,207 passage and 2,838 table nodes (2.90 per question). — [train.traced.json](https://raw.githubusercontent.com/wenhuchen/HybridQA/master/released_data/train.traced.json), [dev.traced.json](https://raw.githubusercontent.com/wenhuchen/HybridQA/master/released_data/dev.traced.json)
- **Ambiguity:**
  - Dev: only 1,890 / 3,466 questions (54.5%) have exactly one answer node, and 2,102 (60.6%) have nodes in a single row. 92 have zero nodes ("computed" answers).
  - Train: 33,463 / 62,682 (53.4%) have one node, 38,394 (61.3%) a single row, and 664 have zero nodes.
  - Example: train question "Who were the builders of the mosque in Herat with fire temples?" (answer "Ghurids") gets 4 passage nodes (Kabul x2, Great Mosque of Herat, Mazar-i-Sharif). This fits the tracer listing every linked passage whose text contains the answer string (my inference from the OTT-QA description quoted below; I did not open those passages).
  - — my parse of the traced files ([train.traced.json](https://raw.githubusercontent.com/wenhuchen/HybridQA/master/released_data/train.traced.json))
- **Noise level, from the HybridQA/OTT-QA authors:** "Since in HybridQA the oracle fine-grained answer span is not explicitly annotated, we approximate this by traversing the table and hyperlinked passages to find all exact matches. This process contains some noise—a manual study reveals that it roughly contains 15% error." — [OTT-QA paper, §3.1](https://arxiv.org/abs/2010.10439)
- The HybridQA paper also says: "The matching process is approximated, not guaranteed to be 100% correct". HYBRIDER trains its ranking and hop models on these "somewhat noisy" synthesized reasoning paths "in a weakly supervised manner". — [HybridQA paper §2, §4](https://aclanthology.org/2020.findings-emnlp.91/)
- There is **no gold reasoning path** (e.g., the bridge cell such as the "second-most rushing yards" row). Only the answer location is traced. My inference from the field list; the paper describes only answer tracing.

**Table and passage statistics** (paper Table 2)
- 13,000 tables; 15.7 rows / 4.4 columns on average; 70 cells; 44 links per table. 293,269 passages averaging 103 words. 69,611 questions averaging 18.9 words. — [HybridQA paper Table 2](https://aclanthology.org/2020.findings-emnlp.91/); the README also says "each table is in average linked to 44 passages" — [README](https://raw.githubusercontent.com/wenhuchen/HybridQA/master/README.md)

**WikiTables-WithLinks format**
- `tables_tok/<table_id>.json`: keys `url, title, header, data, section_title, section_text, uid, intro`. Header and data cells are `[cell_text, [hyperlink1, hyperlink2, ...]]`. `request_tok/<table_id>.json` holds "all hyperlinks within a given table". — [WikiTables-WithLinks README](https://github.com/wenhuchen/WikiTables-WithLinks)
- Verified example:
  - `List_of_National_Football_League_rushing_yards_leaders_0`: 20 rows x 6 columns, 13,299 bytes. Row 0 = `[['1', []], ['Emmitt Smith', ['/wiki/Emmitt_Smith']], ['Dallas Cowboys ( 1990 - 2002 ) Arizona Cardinals ...', ['/wiki/Dallas_Cowboys', '/wiki/1990_NFL_season', ...]], ...]`.
  - Its `request_tok` file is a dict `{"/wiki/Emmitt_Smith": "Emmitt James Smith III ( born May 15 , 1969 ) is an American ..."}` with 89 entries (100,732 bytes).
  - Text is pre-tokenized: spaces around punctuation.
  - — [tables_tok example](https://raw.githubusercontent.com/wenhuchen/WikiTables-WithLinks/master/tables_tok/List_of_National_Football_League_rushing_yards_leaders_0.json); [request_tok example](https://raw.githubusercontent.com/wenhuchen/WikiTables-WithLinks/master/request_tok/List_of_National_Football_League_rushing_yards_leaders_0.json)
- The README notes a past bug fix: "previous tables are indexed by number, now the new tables are indexed by page_name_position, the mapping can be found in orig_id_to_uid.json". — [WikiTables-WithLinks README](https://github.com/wenhuchen/WikiTables-WithLinks)
- No LICENSE file was found in WikiTables-WithLinks (raw `LICENSE` and `LICENSE.md` not found). — [repo](https://github.com/wenhuchen/WikiTables-WithLinks)

**Official evaluation**
- Usage: `python evaluate_script.py predictions.json released_data/dev_reference.json`. Predictions format: `[{"question_id": ..., "pred": ...}]`. — [README](https://raw.githubusercontent.com/wenhuchen/HybridQA/master/README.md)
- `normalize_answer` is SQuAD-style: lowercase, remove punctuation, remove articles `\b(a|an|the)\b`, collapse whitespace.
  - EM = exact match after normalization; F1 = token-overlap F1. There is one gold answer per question.
  - Output keys: `table exact`, `table f1`, `passage exact`, `passage f1`, `total exact`, `total f1`, `total`.
  - The 92 "computed" dev questions count in `total` but in neither subset.
  - — [evaluate_script.py](https://github.com/wenhuchen/HybridQA/blob/master/evaluate_script.py)
- Test scoring is through the CodaLab "HybridQA Competition". Submit a zipped `test_answers.json`; "The reported scores are EM and F1." — [README](https://raw.githubusercontent.com/wenhuchen/HybridQA/master/README.md); [CodaLab competition 7979](https://codalab.lisn.upsaclay.fr/competitions/7979) (page returned HTTP 200 with title "HybridQA Competition" on 2026-10-06)

### Inferences
- **Using the answer nodes for behaviour cloning and the recall reward:**
  - Treat them as a **set of acceptable targets** (multi-positive / any-of), not a single gold action: about 46% of questions have several nodes, and about 15% are wrong.
  - Recall reward: "selected evidence contains at least one answer node" (hit@k), or the fraction of answer rows covered.
  - Behaviour cloning: maximize the log of summed probability over the node set, or pick the node whose row best matches the question.
  - Drop the zero-node (computed) questions from behaviour-cloning data but keep them in evaluation, because the official `total` includes them.
- **Graph size:** using the paper's averages, a per-question entity graph has roughly 70 cells + about 16 rows + about 4 columns + about 44 passages ≈ 130-140 nodes. That is small enough for CPU PPO.
- **Data size:**
  - The full raw table and passage set is about 194 MB zipped. Only tables referenced by the chosen subset need loading: dev uses 3,053 tables.
  - A laptop-feasible protocol: a 5-10K question train subsample, the full 3,466 dev set for reporting, and optionally a CodaLab test submission.
- **Loading route:** the safest path is GitHub raw JSON plus the `WikiTables-WithLinks` clone (or the HF zip mirror), not `load_dataset("hybrid_qa")`. The latter needs `datasets<4.0` with `trust_remote_code=True` and still lacks answer nodes.
- **Licence conflict to report:** code repo MIT, HF card CC BY 4.0, and no licence file in WikiTables-WithLinks. The underlying Wikipedia text is normally CC BY-SA (general knowledge, not verified here).

- I did not run `trace_answer.py` to confirm the exact matching rules (e.g., whether a table node is also emitted when the answer appears in a passage).

## Q2. Published HybridQA results (dev/test EM/F1) for prior systems, with sources, and BibTeX

### Takeaway
- Among fine-tuned systems, the HybridQA leaderboard tops out with S³HQA: 68.4/75.3 dev and 67.9/75.5 test EM/F1.
- The original HYBRIDER baseline scores 43.5/50.6 dev and 42.2/49.9 test (BERT-base); the BERT-large variant scores 44.0/50.7 and 43.8/50.6.
- LLM methods without fine-tuning reach roughly 44-60 EM on dev, but mostly on 200- or 500-question subsets with non-official setups. Those numbers are not directly comparable to the full-dev or test numbers.

### Inferences
- **Which numbers to cite:**

## Q3. MMQA (Wu et al., ICLR 2025): where to download, format, size, licence, gold SQL / PK-FK, published numbers

### Takeaway
- The official MMQA data link in the ICLR camera-ready is an anonymous 4open.science repository that now returns "repository_expired" (HTTP 410). The OpenReview entry has no supplementary-material field, and I found no official GitHub or Hugging Face release.
- A third-party Hugging Face upload (`table-benchmark/mmqa`, Dec 2025, no licence stated) contains 3,313 examples with gold SQL (JOINs), primary-key lists and foreign-key lists.
- The tables are very large (averages of 1,369-1,833 rows), the questions are LLM-generated, and there is no train split. That makes MMQA a risky, evaluation-only secondary benchmark for a laptop-CPU RL project.

### Inferences
- MMQA's gold `SQL` (explicit `JOIN ... ON a.k = b.k` paths) and PK/FK lists are exactly the kind of supervision the project's "joined tables" hops need. Gold evidence can be derived by parsing the SQL (tables, join keys, WHERE predicates) or by executing it on the provided table contents to get the gold rows.
- However:
  - (i) The provenance is a third-party mirror with no licence, and its count is off by one (3,313 vs 3,312).
  - (ii) There is no train/dev split, so behaviour cloning would require self-made splits.
  - (iii) Tables average more than 1,000 rows, so cell-level graphs would be huge; row- and column-level nodes would be needed.
  - (iv) Answers are often lists or aggregates (Numerical, List, Count categories), which suits an SQL executor better than a frozen extractive reader.
- If used at all, MMQA fits a small optional "multi-table transfer" experiment, e.g. the 721-question 3-table file (92 MB). Spider's own licence would also apply; Spider is commonly distributed under CC BY-SA 4.0, but I did not verify that here.

### Gaps
- I could not find any official, permanent MMQA release (GitHub, HF or OpenReview supplementary). The authors may have one I missed; worth emailing the first author.
- Licence: none is stated in the paper or on the third-party HF card.
- The paper does not say what the four "Human" numbers map to (the tables have 7 metric columns).
- I did not verify that `table-benchmark/mmqa` matches the original release exactly (e.g., whether it includes the 2-table file's FK/PK and SQL for all 2,591 items; I parsed only the 3-table file head).

## Q4. OTT-QA, MultiTabQA, TAT-QA, WikiTableQuestions: short datasheets (choose or not)

### Takeaway
None of the four should be a primary benchmark:
- **OTT-QA** is the open-domain version of HybridQA (retrieval over 400K+ tables and 5M+ passages, and no hyperlinks in dev/test), which is too heavy for a laptop.
- **MultiTabQA** produces table-valued answers from Spider/ATIS/GeoQuery with gold SQL. It is small but generative, not evidence-selection.
- **TAT-QA** is finance numerical reasoning with paragraph-level evidence only.
- **WTQ** has single tables with answer denotations and no evidence annotations.

### Inferences
- **OTT-QA:** reject as the main benchmark. The 400K-table / 5M-passage retrieval is outside the RL selection problem and laptop budget, and dev/test tables have no hyperlinks, so the entity graph would need predicted links. It is worth citing as the open-domain extension.
- **MultiTabQA:** the only small (about 7.7K examples) multi-table set with gold SQL on HF. But its outputs are tables and its readers are generative, so it mismatches a frozen extractive reader. At most, mention it as a source of gold JOIN supervision.
- **TAT-QA:** reject. Most answers need arithmetic over one small table, evidence is paragraph-level only, and there are no multi-hop entity links.
- **WTQ:** reject for training. There is no gold evidence for behaviour cloning or the recall reward, and no passages or joins.

- I did not verify the SQUALL dataset (SQL alignments for WTQ) in this session.

## Q5. Small frozen extractive QA readers on Hugging Face for HybridQA-style evidence

### Takeaway
- The reasonable frozen readers are deepset's SQuAD 2.0 models. Ordered by size: `deepset/minilm-uncased-squad2` (33M), `deepset/tinyroberta-squad2` (82M), `deepset/roberta-base-squad2` (124M, the most downloaded), and `deepset/deberta-v3-base-squad2` (184M, best base-size accuracy).
- `roberta-base-squad2` is the safest default; `tinyroberta`/`minilm` suit CPU-bound PPO rollouts.
- Published HybridQA systems fine-tune their own BERT readers, so I found no published "frozen SQuAD reader on HybridQA" number.

- How published HybridQA systems read:

### Inferences
- **Recommended setup:**
  - Freeze `deepset/roberta-base-squad2` (or `tinyroberta-squad2` when rollout speed dominates).
  - Linearize the selected evidence, e.g. "row: col1 is v1; col2 is v2 ... [SEP] passage text", into one context of at most 384 tokens.
  - Read the span. When the selected node is a table cell (about 42% of questions are In-Table), also allow a "copy the cell value" action.
- **Why SQuAD2 rather than SQuAD1.1:** SQuAD2 readers can abstain, which gives a usable "insufficient evidence" signal for the reward and for stop actions. That is an advantage over SQuAD 1.1-only DistilBERT.
- **CPU cost:** roughly 0.1-0.3 s per 384-token forward pass for 82-124M models is a typical order of magnitude, but I did not benchmark it. Caching reader outputs per (question, evidence set) would be essential for PPO.

### Gaps
- I found no paper reporting HybridQA EM for an off-the-shelf frozen SQuAD 2.0 reader with oracle or selected evidence. The project would need to measure its own oracle-evidence upper bound, e.g. reader on the gold answer-node passage or cell.
- I did not extract deepset/electra-base-squad2's SQuAD2 scores, and I did not measure CPU latency.
